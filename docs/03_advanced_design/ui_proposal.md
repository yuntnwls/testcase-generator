# UI 화면 설계

본 문서는 지능형 엔진(Next-Gen)의 통합 프로그램에 필요한 모든 인터페이스 화면을 정의합니다. 엔지니어가 직접 스크립트를 변환하는 **실행 화면(Execution UI)**과, 시스템의 지식 베이스를 관리하고 확장하는 **관리 화면(Management Hub)**으로 나뉘어 구성되며, 직관성을 돕기 위한 텍스트 Mockup(모의 화면)을 포함합니다.

---

## 1. 실행 및 모니터링 화면 (Execution & Dashboard)

사용자가 일상 업무에서 TC 엑셀을 업로드하고 결과를 모니터링하는 주력 화면입니다.

### 1-1. 메인 대시보드 (Dashboard)
*   **왜 필요한가 (Necessity)**:
    - 지능형 엔진은 단순한 스크립트 실행기가 아니라 스스로 지식(Vector 템플릿, Ontology)을 쌓아가는 유기적인 시스템입니다.
    - 관리자는 현재 시스템이 얼마나 많은 지식을 학습했는지(성장도), 그리고 오늘 하루 자동화의 신뢰성(변환 성공률 및 LLM 캐시 효율성)이 어떠한지 거시적인 지표(Health Check)를 한눈에 파악해야 합니다.
*   **업무 흐름 (Workflow)**:
    1.  시스템 접속 시 가장 먼저 대시보드를 확인합니다.
    2.  `변환 성공률`이 급감했거나 `캐시 Hit-Ratio`가 떨어졌다면, 시스템이 '모르는 문장'이 대거 등장했다는 뜻이므로 템플릿이나 지식 점검의 필요성을 인지합니다.
    3.  가운데 위치한 `승인 대기열(Approval Queue)` 알림을 보고, AI가 처리하지 못한 보류 안건이 있는지 점검하러 이동합니다.
*   **Mockup**:
    ```text
    ================================================================================
    📊 [Dashboard] - Next-Gen Automation Hub
    ================================================================================
    [오늘의 변환 현황] 
    ✅ 성공: 1,420건 (98.6%)  |  ❌ 복구 실패: 20건 (Action Required)
    ⚡ 템플릿 캐시 Hit-Ratio: 45.2% (평균 변환속도 0.8초/TC)

    [시스템 지식 상태]
    🧠 관할 차종 스펙: 14종 (최근 Ingestion: CarModel_C, 어제 14:00)
    📚 Vector 템플릿: 420개 (SIMVA: 300, CAPL: 120)
    ⚠️ AI 구출 대기열 (Approval Queue): 12건의 미처리 안건 대기 중! [바로가기]
    ================================================================================
    ```

### 1-2. 배치 변환기 (Batch Converter)
*   **왜 필요한가 (Necessity)**:
    - 수백~수천 줄 단위의 엑셀/TSV 테스트 케이스를 사람이 일일이 코드 단위로 번역하는 단순 반복 작업을 없애기 위함입니다.
    - 변환 도중 예외가 발생하더라도 전체 프로세스가 뻗지 않고(Isolation), 실시간으로 어떤 TC가 변환 중인지 진행률을 투명하게 보여주어 작업자의 대기 피로도를 줄여야 합니다.
*   **업무 흐름 (Workflow)**:
    1.  검증 엔지니어가 작성한 자연어 TC 파일(Excel/TSV)을 업로드합니다.
    2.  `변환 타겟(SIMVA/CAPL 등)`과 `대상 차종(Variant)`을 선택하여 엔진에게 번역의 '문맥(Context)'을 던져줍니다.
    3.  [변환 시작]을 누르면 백그라운드에서 동적 배치(Dynamic Batching)가 돌며 코드를 쏟아냅니다.
    4.  화면 하단의 `실시간 로그`를 통해 캐시 Hit로 빠르게 넘어가는 작업과 LLM이 에러를 자가 복구(Self-Correction)하는 과정을 지켜봅니다.
    5.  변환이 끝난 정상 스크립트를 다운로드하여 IDE로 가져가고, 실패한 케이스는 '승인 대기열'로 이관된 것을 확인합니다.
*   **Mockup**:
    ```text
    ================================================================================
    ⚙️ [Batch Converter] - 스크립트 대량 변환 실행
    ================================================================================
    📂 Upload: [ Body_Control_TC.xlsx ⬇️ ]
    🎯 Target: (O) SIMVA Python   ( ) CAPL CANoe   ( ) vTESTstudio
    🚗 Variant: [ CarModel_A_2024 ▼ ]  (지식 그래프 종단점 선택)

    ▶️ [ 변환 시작 (Start Conversion) ]
    --------------------------------------------------------------------------------
    [진행률] 🟩🟩🟩🟩🟩🟩🟩🟩⬜⬜ 80% (800 / 1000 TC)  [취소]
    
    [실시간 로그 (Dynamic Batching)]
    > [TC_001] 변환 성공 (Hit Cache) - 0.1sec
    > [TC_002] 변환 성공 (Vector Search) - 1.2sec 
    > [TC_003] 구문 에러 발견 -> (Self-Correction 시도 1/3) -> 복구 성공! - 3.5sec
    > [TC_004] [FAIL] 알 수 없는 시그널 '선루프_2단' 발견 (Isolation) -> Queue 이관
    ================================================================================
    ```

## 2. 지식 관리 허브 (Management Hub)

엔진이 스스로 학습하고 문맥을 파악하는 과정에서, 인간 관리자(Domain Expert)가 개입하여 엔진을 가르치고 에러를 통제하는 화면입니다.

### 2-1. 자연어 템플릿 빌더 (Vector DB Manager)
*   **왜 필요한가 (Necessity)**:
    - 테스터(비개발자)가 현장에서 새로운 방식의 문장을 사용하더라도 개발자의 개우 없이 UI 상에서 직접 "문장-코드" 매핑 뼈대를 정의하고 지식을 확장하기 위해 필수적인 화면입니다.
*   **업무 흐름 (Workflow)**:
    1.  배치 변환 중 계속해서 에러를 뱉는 "완전히 낯선 문장 패턴"을 발견합니다.
    2.  `Vector DB Builder` 화면으로 들어와 낯선 문장(원본)을 그대로 붙여 넣습니다.
    3.  문장 내에서 값이 바뀔 부분(ex: `열선`, `3`)을 마우스로 드래그하여 변수(`{signal_name}`, `{value}`)로 치환시킵니다.
    4.  하단에 해당 패턴이 최종 번역될 정답 코드 타겟 템플릿(ex: `simva.set_signal()`)을 작성합니다.
    5.  [배포] 버튼을 누르면 내부 API가 정규식(Regex)을 자동 합성하여 Vector DB에 밀어 넣습니다. 다음 번 호출부터는 이 템플릿이 즉각 적용(Hot-Reload)됩니다.
*   **Mockup**:
    ```text
    ================================================================================
    🛠️ [Vector DB Builder] - 신규 패턴 학습
    ================================================================================
    1️⃣ [Input] 새롭게 추가할 자연어 테스트 문장을 입력하세요.
    📝 원본: [ 시트 열선을 3단으로 가동한다                            ]
    --------------------------------------------------------------------------------
    2️⃣ [Mapping] 가변적인 단어를 마우스로 드래그(Drag)하여 변수로 지정하세요.
    🖱️ 드래그한 문장: [시트 열선]을 [3]단으로 가동한다
       └─ 지정 결과:  [ {signal_name} ]을 [ {value} ]단으로 가동한다
    --------------------------------------------------------------------------------
    3️⃣ [Target] 타겟 코드 템플릿을 작성하고 변수를 꽂아 넣으세요.
    💻 코드:   [ simva.set_signal(signals.{ecu}.{signal_name}, "{value}") ]
    
    [ 💾 Vector DB에 즉시 배포 (Hot-Reload 반영) ]
    ================================================================================
    ```

### 2-2. 지식 그래프 익스플로러 (Ontology Explorer)
*   **왜 필요한가 (Necessity)**:
    - 자동차 도메인은 차종마다 물리 시그널 이름이 다 다르고(ex: A차는 `CGW_VSpd`, B차는 `ESP_Speed`), 현장 직원마다 같은 걸 뜻하는 은어(Alias)가 다양합니다("차속", "스피드").
    - 이 거대한 다형성을 제어하기 위해 모든 지식을 통합한(Concept 노드 중심) 그래프를 수시로 오디팅(Auditing)하고 교정해야 합니다.
*   **업무 흐름 (Workflow)**:
    1.  검색창에 문제의 단어(예: "차량 속도")를 검색합니다.
    2.  이 논리적 개념(Concept) 노드를 중심으로 하위에 엮인 진짜 물리 시그널(차종별) 그래프 트리를 시각적으로 펼쳐 누락된 시그널 연결이 없는지 확인합니다.
    3.  만약 테스터가 자꾸 "스피드"라는 비표준 단어를 써서 매핑이 실패했다면, 해당 노드를 클릭하여 디테일 패널에서 "스피드"를 동의어(Alias)로 추가 저장합니다. 
    4.  이렇게 저장된 은어는 추후 지능형 엔진 파싱 과정에서 정규화 치환(Normalization) 데이터로 즉각 쓰입니다.
*   **Mockup**:
    ```text
    ================================================================================
    🕸️ [Ontology Explorer] - 지식망 구조 및 별칭 사전
    ================================================================================
    🔍 검색: [ 차량 속도 ]
    
    [Graph View]
               (Logical) [Concept:VehicleSpeed]
                  /                           \
     (Variant:Car_A)                        (Variant:Car_B)
           /                                      \
    (Physical) [CGW_VehSpd_Main]             (Physical) [ESP_Speed_FR]

    --------------------------------------------------------------------------------
    [디테일 패널 (Alias 관리)]
    선택된 노드: [Concept:VehicleSpeed]
    📝 등록된 동의어/은어 (Natural Language Aliases):
    - "차속", "스피드", "주행속도"  [+ 새 단어 추가]
    
    📝 Value 정규화 규칙(Values):
    - [100] -> "고속", "빠르게"
    - [0]   -> "정지", "멈춤" [+ 새 단어 추가]
    ================================================================================
    ```

### 2-3. AI 승인 대기열 (AI Approval Queue)
*   **왜 필요한가 (Necessity)**:
    - 4단계 Fallback 시스템에서는, 배치가 돌아가다 에러가 나면 멈추는 대신 LLM이 "제가 가장 비슷한 걸로 한 번 추측해봤습니다" 하고 임의의 결정을 내립니다. 
    - 이 임의 결정은 그 순간 위기를 모면하게 해주지만, 영구 지식 베이스로 넣기 전 인간(Human-in-the-loop) 도메인 전문가의 검증이 필요합니다.
*   **업무 흐름 (Workflow)**:
    1.  대시보드 알람을 통해 큐(Queue)에 들어옵니다.
    2.  `[Case 1]`처럼 AI가 자신이 모르는 단어("햇빛가리개")를 기존의 아는 개념([Concept:SunVisor])과 매핑한 제안 리스트를 쭉 훑어봅니다.
    3.  AI의 판단이 맞다면 `[✅ 승인(Approve)]`을 누릅니다. -> **Ontology Explorer의 Alias 목록에 자동 저장**되며 영구 지식이 됩니다. 다음번엔 LLM 호출조차 필요 없어집니다!
    4.  만약 AI 판단이 틀렸다면 `[❌ 거절(Reject)]`을 누르거나 `[✏️ 수정]`으로 올바른 노드에 할당시킵니다.
*   **Mockup**:
    ```text
    ================================================================================
    ⚖️ [Approval Queue] - AI 판정 승인 대기열 (미처리: 2건)
    ================================================================================
    [Case 1] 온톨로지 시그널 매칭 실패 구출
    - 출처: TC_BODY_044 ("햇빛가리개를 활짝 연다")
    - 문제: 지식 그래프에 "햇빛가리개"가 없음.
    - AI 유추: 의미론적 탐색 결과, DB 내 [Concept:SunVisor] 와 98% 일치.
    - 제안: "햇빛가리개"를 [Concept:SunVisor]의 Alias로 영구 등록합니까?
    👉 [ ✅ 승인(Approve) ]  [ ❌ 거절(Reject) ]  [ ✏️ 직접 수정 ]

    [Case 2] 논리/타입 에러 치명적 장애 (Human Handoff)
    - 출처: TC_POWER_011 ("IG ON 상태에서...")
    - 문제: 3회 Self-Correction 실패. (타겟 ECU 불명 판정)
    👉 [ 🔍 Trace Analyzer로 이동하여 수동 디버그 ]
    ================================================================================
    ```

### 2-4. 변환 트레이스 분석기 (Trace Analyzer)
*   **왜 필요한가 (Necessity)**:
    - 지능형 시스템에서는 자연어에서 코드로 즉시 합성(Direct Synthesis)되기 때문에, 만약 결과(코드)가 엉뚱하게 도출되면 이게 템플릿 검색에서 틀린 건지(Retriever 에러), 값을 잘못 뽑은 건지(Extractor 에러), 온톨로지 단어가 단절된 건지 원인을 파악하기 위해 단계별 추적이 필수적입니다.
    - 이를 위해 변환기의 내부 4단계 의사결정 체계(Pipeline)를 투명한 X-ray처럼 스텝별로 들여다볼 수 있는 개발/디버깅 도구가 필요합니다.
*   **업무 흐름 (Workflow)**:
    1.  `승인 대기열(Screen 3)`에서 AI마저 포기해버린 치명적 장애(Fail) 케이스의 `Trace ID` 링크를 클릭해 넘어옵니다.
    2.  `[Step 1]` 유사도 매칭이 잘 되었는지(Score 확인), `[Step 2]` 변수 쪼개기가 정규식에서 이탈하지 않았는지 차근차근 점검합니다. 
    3.  에러가 난 `[Step 3]` 구역을 시각적으로 짚어내고, "아, '매우 빠르게'라는 표현을 정수 값으로 변환하는 Alias 테이블이 없었구나"라는 근본 원인(Root Cause)을 깨닫습니다.
    4.  곧바로 `Ontology Explorer(Screen 2)` 창으로 넘어가 맵핑을 보완하여 결함을 영구 삭제합니다.
*   **Mockup**:
    ```text
    ================================================================================
    🔎 [Trace Analyzer] - 의사결정 스텝 디버거
    ================================================================================
    🏷️ 문장: "와이퍼를 매우 빠르게 켠다"
    
    [Step 1] Vector DB Retriever
    🎯 매칭 템플릿: "와이퍼를 {val} 속도로 켠다" (유사도 Score: 0.92) - OK
    
    [Step 2] 하이브리드 Extractor
    ✂️ 변수 추출: {val} = "매우 빠르게" - OK
    
    [Step 3] Ontology Mapper & Normalization 
    ❌ 에러 발생: "매우 빠르게"라는 별칭이 매핑된 Value Code(정수)가 없음.
       -> [LLM Semantic Search 트리거 됨] 
       -> LLM 제안: Value(3) (신뢰도 85%) - 적용됨
    
    [Step 4] Assembler
    🧩 최종 조립: simva.set_signal("Wiper_Speed", 3)
    ================================================================================
    ```

### 2-5. 시스템 환경 설정 (System Settings / LLM Config)
*   **왜 필요한가 (Necessity)**:
    - AI 시대에는 언어 모델 발전 속도가 매우 빠르므로, 시스템 기동 중에도 언제든지 더 똑똑하거나 빠른 최신 LLM(OpenAI, Ollama 등)으로 쉽게 엔진을 교체(Hot-Reload)할 수 있어야 합니다.
    - 보안 부서 정책에 따라 외부 API망이 막히면 즉각 로컬 모델(Local LLM)로 우회하도록 엔지니어가 직접 스위치(Toggle)를 켤 수 있어야 합니다.
*   **업무 흐름 (Workflow)**:
    1.  대시보드 좌측 메뉴의 ⚙️ [설정] 아이콘을 통해 진입합니다.
    2.  `LLM 제공자(Provider)` 드롭다운에서 `OpenAI`를 선택하면 자동으로 하위 메뉴가 OpenAI 연동에 필요한 `API Key`와 `Model(ex: gpt-4o)` 입력란으로 갱신됩니다.
    3.  사내망에서 오프라인 모드로 돌려야 할 경우, 드롭다운을 `Local (Ollama)`로 바꾸고 사내망 Endpoint와 구동 중인 모델 체급(`llama3:8b`)을 고릅니다.
    4.  [적용 후 재시작] 버튼을 누르면 내부 Factory 객체가 새 모델로 스위칭되어 다음번 Batch 변환부터 즉각 적용됩니다.
*   **Mockup**:
    ```text
    ================================================================================
    ⚙️ [System Settings] - 지능형 엔진 및 보안 설정
    ================================================================================
    [ 🤖 LLM Engine Configuration ]
    현재 활성 프로바이더: [ 🟢 OpenAI API (gpt-4o) ]
    ```
